## Known limitations (stated explicitly, per PRD §6 item 3)

1. **N=1 per condition, single grading pass** — as the PRD itself flags,
   inherited from `evidence-driven-engineering`'s own documented
   limitation.
2. **The 14 baseline responses in this report are CONTAMINATED.** They
   were generated by Claude sessions (the parent session and 3 forked
   subagents it spawned) that had, earlier in the same conversation,
   read every `ios-tuist-*` `SKILL.md` and every fixture's
   `EXPECTATIONS.md` multiple times. A genuinely naive baseline
   (fresh `claude` session, no `--plugin-dir`, no prior exposure to this
   repo's skill content) was not used. **These 14 responses are
   reference/scaffolding material only — not evidence for a rubric
   score or a real with-skill-vs-baseline verdict.** Real baseline runs
   (per `EXECUTION-GUIDE.md`) are needed before any comparison in this
   report can be trusted.
3. **The with-skill condition cannot be run from inside this session.**
   A spike confirmed that a subagent spawned via the `Agent` tool does
   not see any `ios-tuist-*` skill (this plugin loads into the parent
   session only via `--plugin-dir`, and that does not propagate to
   subagents). With-skill runs require the user to start a separate
   `claude --plugin-dir /Users/dave/Documents/GitHub/ios-tuist-skills`
   session per comparison, per `EXECUTION-GUIDE.md`.
4. **14 comparisons, not 12** — the PRD's original draft undercounted
   (see its §4.2 correction note); this reflects the corrected count.

Even without rubric scoring, three findings from the raw reports are
worth carrying into the real (uncontaminated) baseline runs as things
to specifically watch for, since they recurred across multiple
contaminated runs:

1. **Version-pin awareness gap** (`legacy-tuist`, `version-mismatch`):
   `mise` auto-resolving the correct toolchain silently masks whether
   the response *itself* ever explicitly detected/reported the pin —
   this is exactly the failure mode `ios-tuist-feature`'s Decision
   Rules and the rubric's item 1 (version/convention detection) are
   designed to catch, and it reproduced even in a contaminated run.
2. **App-scheme testAction under-coverage** (`new-project`,
   `architecture-smells`): a scheme generated without deliberately
   wiring every feature module's test target into the app scheme's
   `testAction` silently under-runs tests when a user just runs
   `xcodebuild test -scheme App`. Worth checking whether a real
   with-skill run avoids this by construction.
3. **Approve-before-apply skipped** (`ci-gaps`): the contaminated
   baseline found the right diagnosis but applied the fix without a
   proposal/approval step — a concrete instance of the exact behavior
   `ios-tuist-ci` exists to enforce.
