## What this response did

- Inspected `Project.swift` before acting. It defines exactly two
  targets (`App`, `AppTests`) with no existing feature-module split —
  there is no pre-existing "one target per feature" convention in this
  project to follow, only a single flat target with glob-based source
  inclusion.
- Judgment call: added `LoginFeature` as a **new folder inside the
  existing `App` target** (`App/Sources/LoginFeature/LoginView.swift`,
  `App/Sources/LoginFeature/LoginViewModel.swift`), not as a new Tuist
  target/module. Rationale used: the project's own convention is "one
  target, globbed sources" — introducing a second target for a single
  new screen would be inventing a modular pattern the project doesn't
  already have, which reads as scope creep for a one-line feature
  request. Because `Project.swift`'s `sources: ["App/Sources/**"]` glob
  already covers the new subfolder, **no manifest edit was needed or
  made**.
- Added `App/Tests/LoginViewModelTests.swift` using the existing XCTest
  convention (`import XCTest`, `@testable import App`), matching
  `AppTests.swift`'s style exactly. Covered by the same
  `sources: ["App/Tests/**"]` glob — again, no manifest edit.
- Did not touch `.tool-versions`, did not switch anything to
  `buildableFolders`, did not introduce Swift Testing, did not touch
  `Tuist.swift`.
- Did **not** explicitly reconcile the `.tool-versions` pin (4.206.0)
  against whatever `tuist` was active on `PATH` before running
  commands — see Real verification section; this was noticed only
  during the verification step, not called out as a decision point in
  the implementation step itself.
