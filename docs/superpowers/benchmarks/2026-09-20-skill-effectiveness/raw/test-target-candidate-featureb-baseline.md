## What this response did

- Inspected `Project.swift` first and confirmed `FeatureB` has no
  associated test target and is not present in the `App` scheme's
  `testAction` (only `buildAction`).
- Looked at the sibling feature module, `FeatureA`/`FeatureATests`, to
  infer the project's existing test-target convention rather than
  inventing one: `product: .unitTests`, `sources:
  ["FeatureA/Tests/**"]`, single `dependencies: [.target(name:
  "FeatureA")]`, and — notably — Swift Testing (`import Testing`,
  `@Suite`/`@Test`) rather than XCTest, even though the `App` target's
  own `AppTests` uses XCTest. Followed the **feature-module sibling's**
  convention (Swift Testing) for the new `FeatureBTests`, reasoning
  that `FeatureB` is architecturally the same kind of target as
  `FeatureA`, not as `App`.
- Created `FeatureB/Tests/FeatureBTests.swift`:
  ```swift
  import Testing
  @testable import FeatureB

  @Suite struct FeatureBTests {
      @Test func labelIsStable() {
          #expect(FeatureBLabel.text == "FeatureB")
      }
  }
  ```
  — one placeholder-style test, mirroring `FeatureATests`' own
  single-assertion shape and asserting against the one real symbol
  `FeatureB/Sources/FeatureB.swift` already exposes (`FeatureBLabel.text`).
- Added a new `.target(name: "FeatureBTests", product: .unitTests, ...,
  dependencies: [.target(name: "FeatureB")])` declaration to
  `Project.swift`, placed directly after the `FeatureB` target
  declaration (matching the existing `FeatureA`/`FeatureATests`
  ordering pattern).
- Edited the `App` scheme's `testAction` from `.targets(["AppTests",
  "FeatureATests"])` to `.targets(["AppTests", "FeatureATests",
  "FeatureBTests"])` — appended, did not replace the existing list.
- Left `buildAction` and `runAction` on the scheme untouched, and left
  every other target's declaration (`App`, `AppTests`, `FeatureA`,
  `FeatureATests`) byte-identical.
